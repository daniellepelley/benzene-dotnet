# Capability Matrix — what Benzene does, deliberately doesn't, and how to fill the gap

Benzene is honest about its boundaries. This page is the single place that states, for each
common production concern, **what Benzene provides**, **what it deliberately does not do (and
why)**, and **how to solve the rest outside Benzene**. Nothing here is a hidden gap — these are
design decisions that follow directly from Benzene's philosophy.

## The one idea behind every row

Benzene abstracts at the **business-logic boundary** — you write a message handler once and host
it anywhere — and **never at the transport or storage boundary**. This is the opposite of
frameworks like Dapr that hide the third party behind a generic interface (a "queue", a "state
store") and, in doing so, hide that third party's best features. If you wrap SQS behind a generic
queue interface, you lose the SQS-specific capabilities that were the reason to choose SQS.

So Benzene's answer to "does it abstract X?" is usually a deliberate **no** — you keep full,
direct access to the underlying SDK and all its cloud-native capabilities, and Benzene stays out
of the way. When Benzene doesn't ship an adapter for something, **rolling your own is a
first-class, supported path**: a small piece of middleware or a custom pipe into the pipeline, not
an escape hatch.

Two corollaries you'll see below:

- **A database is not a transport.** Benzene delivers events *in* (an ingress adapter), but it
  does not do database access. Persisting state is your handler's own code (`CosmosClient`,
  EF Core, Dapper, the AWS SDK, …).
- **Some problems can't be solved at runtime inside Benzene at all.** Benzene instances are
  independent processes (separate Lambda invocations, separate containers) that don't know about
  each other. Anything requiring cross-instance coordination (distributed idempotency,
  exactly-once) needs external shared state with atomic semantics — and even then, races are
  inherent. Benzene won't pretend otherwise.

## The matrix

| Capability | What Benzene provides | What it deliberately does NOT do (and why) | How to solve the rest |
|---|---|---|---|
| **Transport features** | Full, direct access to the underlying SDK message/context on every adapter | Hide transport-specific capabilities behind a generic interface (the anti-pattern above) | Use the raw SDK feature directly — the context exposes the native message/event |
| **Message routing** | Topic-based dispatch to `[Message]` handlers; the same handler runs behind every transport. `.UsePresetTopic()`/`.UseTopicFrom()` (fix a topic, or derive it per-message) work on every AWS Lambda trigger package with per-record topic routing — SQS, SNS, S3, DynamoDB Streams, Kafka, and EventBridge alike — plus the other non-HTTP transports listed in `UseTopicFrom`'s own doc comment | Impose a canonical message envelope on transports that already carry routing (Kafka topic, Service Bus properties). Kinesis (`Benzene.Aws.Lambda.Kinesis`) has no preset/derived-topic support and never will by the same design: it fans a batch *in* to one `StreamContext<KinesisEventRecord>` with no per-record topic-routing concept at all, so there is no topic getter to wrap — not a gap, a consequence of the fan-in shape (see its own `CLAUDE.md`) | For envelope-less transports (Queue Storage, Event Hubs bodies) use the Benzene envelope or a preset topic; otherwise route on the native key. For Kinesis, route within the stream handler itself (e.g. on `PartitionKey`) |
| **Idempotency** | `IIdempotencyStore` seam + `InMemoryIdempotencyStore` (single-process) + atomic-claim middleware. Every claim is **fenced**: a win returns an opaque `ClaimToken` that `CompleteAsync`/`ReleaseAsync` require back, so a settle whose token no longer matches the live claim (reclaimed by another worker, or already settled) is refused (`false`, nothing written) rather than clobbering the current holder. `IdempotencyMiddleware` forwards the ambient `CancellationToken` (via `ICancellationTokenAccessor`) into every store call, matching the sibling `Benzene.ClaimCheck` middleware, so a wrapping `UseTimeout`/shutdown actually bounds a slow store call. `IdempotencyMiddleware`'s outcome check now applies the SAME "null == failure, redeliver" convention every transport uses (SQS/DynamoDb always had it; SNS/S3/EventBridge got it in round 15's #229): a result-bearing (`IHasMessageResult`) context that completes without the pipeline ever setting `MessageResult` is treated as NOT proven successful and releases the claim, rather than being silently recorded `Completed` and permanently suppressing a real redelivery (round 16, #260 — the old fall-through disagreed with every transport it sits in front of). **Fencing is token match alone** across every implementation (`InMemoryIdempotencyStore`, `DynamoDbIdempotencyStore`, both Outbox stores) — a holder that merely outraces its own TTL, with nobody having reclaimed the key, can still settle with its original token. `DynamoDbIdempotencyStore.TryClaimAsync` never reports a win it didn't write: a conditional `PutItem` that loses to a live record which then reads back absent (a race with a concurrent release) is bounded-retried rather than synthesized as a win — every `Won` corresponds to an actual successful write. | Cross-instance de-duplication — independent processes can't coordinate at runtime without external state, and adding shared state can just relocate the race, not remove it | An external store with an **atomic conditional write** (DynamoDB conditional put, Redis `SET NX`) keyed on message identity, **plus** handlers designed to be naturally idempotent. See [Idempotency](cookbooks/idempotency.md). |
| **Outbox (produce-side durability/atomicity)** | `UseOutbox()` route middleware (`Benzene.Outbox`) with two write modes: **`Immediate`** (default) durably stores-and-forwards the send — survives process death/transport outages, retried with backoff, never silently swallowed, but **not** atomic with the handler's own state write; **`Transactional`** stages the envelope and defers the write to a store's own unit of work. Delivery is always **at-least-once**, never exactly-once, and has **no ordering guarantee** across envelopes. Every claim is **fenced**: `ClaimDueAsync`/`ClaimAsync` stamp a `LeaseToken` that `MarkDispatchedAsync`/`RescheduleAsync`/`ParkAsync` require back, closing the live-but-slow-claimant hole (a lapsed lease reclaimed by another worker can no longer have its settle clobbered by the original, stale claimant) — it does not and cannot recall a message a stale claimant already handed to the transport before its lease lapsed. | Make `Transactional` mode's atomic commit real on its own — that needs a store package. Exactly-once delivery, or any ordering guarantee across envelopes (both explicitly out of scope, not just unbuilt). Crash-after-send remains an inherent at-least-once window — fencing narrows it, it does not close it. | For the atomic commit, add `Benzene.Outbox.DynamoDb` (one `TransactWriteItems` via `IDynamoDbOutboxTransaction`) or `Benzene.Outbox.EntityFramework` (same-`DbContext` change tracker + your own `SaveChangesAsync`). At-least-once delivery means consumers **must** dedup — pair every outboxed route with [Idempotency](cookbooks/idempotency.md) on the receiving end (the outbox stamps an `idempotency-key` header by default so the two packages click together with zero extra config). See [Transactional Outbox](cookbooks/transactional-outbox.md). |
| **Resilience** | `UseRetry` — retry with exponential backoff, an optional max-delay cap, and pluggable jitter (`RetryMiddleware.FullJitter()`); `UseTimeout` — a deadline that becomes a `timeout` failure result while a genuine host cancellation still propagates, correctly classified even under nested `UseTimeout` composition regardless of which layer's timer actually fired; or the **sequential-attempt** subset of the Polly toolkit (retry, timeout, circuit breaker, rate limiting) via `Benzene.Resilience.Polly`'s `.UseResiliencePipeline(...)`, including a `.ExcludingCancellation()` `PredicateBuilder` helper so widening a strategy's `ShouldHandle` (e.g. a circuit breaker) doesn't silently drop Polly's own cancellation-safe default. Polly's per-attempt `CancellationToken` (Timeout/RateLimiter) reaches downstream code too — `PollyResilienceMiddleware` exposes it via the same ambient `ICancellationTokenAccessor` `UseTimeout` uses, linked with any outer ambient token so neither is lost; like `UseTimeout`, this only cancels work that actually reads the accessor's token. `PollyResilienceMiddleware` guards against re-entrancy: if a concurrent-attempt strategy (built via Polly's own `AddStrategy(...)` extensibility point — Hedging/Fallback can't even be built against the non-generic builder this package hands out) starts a second attempt while one is in flight, it throws `NotSupportedException` rather than running the downstream pipeline twice against the shared context/token (#267). | Hedging and Fallback are **not supported** — they're generic-`TResult`-only in Polly.Core 8.5.0 (this package's builder is non-generic, since Benzene results flow through the mutable context, not a `TResult`), and, more fundamentally, this middleware shares one `next` continuation/context/ambient token across attempts, which only concurrent-attempt strategies (Hedging is the paradigm case) would violate — see [Polly Resilience Pipelines](cookbooks/polly-resilience.md#why-concurrent-attempt-strategies-arent-supported). Benzene does not re-implement or hide Polly behind its own abstraction — the Polly package runs *your* `ResiliencePipeline`, exposing its full configuration surface for the strategies it does support | For retry/timeout with zero extra dependency use `UseRetry`/`UseTimeout`; for anything more (within the sequential-attempt set) add `Benzene.Resilience.Polly` and drop a Polly `ResiliencePipeline` into `.UseResiliencePipeline(...)` — it even bridges a returned failure result to Polly's outcome model. For hedging-style concurrent calls, implement it at a different layer (around, not through, this middleware). See [Polly Resilience Pipelines](cookbooks/polly-resilience.md) and [Resilience](resilience.md). |
| **Oversized payloads (transport size limits)** | `Benzene.ClaimCheck` — an optional offload/hydrate middleware pair: `UseClaimCheck()` offloads a payload over a configurable threshold to a pluggable `IClaimCheckStore` and carries a reference on the `benzene-claim-check` header; `UseClaimCheck<TContext>()` resolves it back before deserialization, forwarding the ambient `CancellationToken` (via `ICancellationTokenAccessor`) into every store call so a wrapping `UseTimeout`/shutdown actually bounds it. Store packages: `Benzene.ClaimCheck.Aws.S3`, `Benzene.ClaimCheck.Azure.Blob`. The built-in `InMemoryClaimCheckStore` reclaims an expired entry when it is next read, and separately sweeps all expired entries on `PutAsync` (at most once per minute) so a payload that is never read back at all still gets reclaimed, without a background thread. | Compression (a smaller payload avoiding offload entirely), delete-on-consume (fan-out and at-least-once redelivery make it unsafe — see the doc), and interop with a third party's own offload wire format (e.g. the SQS Extended Client Library rides its reference in the body, not a header, so it isn't a drop-in swap) | Retention is TTL-based, sized to exceed queue retention plus any DLQ redrive window (an infrastructure lifecycle rule, not created by the package). See [Claim Check](claim-check.md). |
| **Sagas / workflows** | In-process, compensation-based saga with LIFO rollback (`Benzene.Saga`). A built `Saga` (`SagaBuilder.Build()`) is an immutable descriptor tree — no per-execution outcome is ever stored on its stages/steps — so the same built `Saga` instance is safe to call `RunAsync()` on concurrently, any number of times, without one run's outcome corrupting another's. The all-or-nothing guarantee also covers the optional `ISagaStateStore`: a persistence failure after an effect-producing stage completed triggers the same compensation path as a step failure (`RolledBack`/`PartiallyRolledBack` with the store's exception on `SagaResult.StateStoreException`), not a raw throw — except a failure recording the very start of a run, before anything has executed, which still propagates (nothing to compensate). Every failed step in a failing stage is surfaced via `SagaResult.Failures`, not just the first — `Failure`/`FailureException` remain convenience views over its first entry. | Durable crash-resume — the saga is in-memory `Func` closures that can't be re-hydrated after a process dies; the state store records progress for *observability*, not recovery | For crash-durable, long-running or human-in-the-loop workflows, use a real durable orchestrator: AWS Step Functions, Azure Durable Functions, Temporal, or similar. Benzene's `Benzene.Clients.Aws.StepFunctions` package can *start* a Step Functions execution from a handler, but running/resuming the workflow itself is the orchestrator's job, not Benzene's. See [Sagas](cookbooks/sagas.md). |
| **Schema evolution** | The Confluent wire-format codec (solid, tested) + an `ISchemaRegistryClient` seam | Structural Avro/JSON backward-compatibility checking in-box — the shipped `TextualSchemaCompatibilityChecker` only accepts byte-identical schemas. `SchemaRegistrySerializer.Deserialize` also does not validate the framed schema id against the caller's requested `Type` — it's producer-side interop framing, not registry-driven consumer resolution, so a corrupted/misrouted payload deserializes as whatever type the caller asked for rather than being rejected | Point at a real schema-registry server, or supply your own `ISchemaCompatibilityChecker`. See [Schema Registry](cookbooks/schema-registry.md). |
| **Database / state access** | *(nothing — by design)* | Any database or state-store abstraction — a database is not a transport, so wrapping one would hide its capabilities (the core anti-pattern) | Your handler uses its own SDK/ORM directly (`CosmosClient`, EF Core, Dapper, `DynamoDBContext`, …). Benzene delivers the event in; persistence is yours |
| **Configuration & secrets** | Provider-agnostic `ISecretStore` (env vars, mounted files, composed, cached) + fail-fast startup validation | Ship maintained cloud secret-store adapters (Key Vault / Secrets Manager / SSM) as packages | Copy the ~30-line adapter from [Secrets & Configuration](cookbooks/secrets-configuration.md) and reference the cloud SDK yourself (a shipped adapter is a candidate for post-1.0) |
| **Outbound HTTP** | `Benzene.Clients.Http` middleware over an `HttpClient` you supply | Manage `HttpClient` lifetime for you (no built-in `IHttpClientFactory` wiring on the low-level path) | Register a typed/`IHttpClientFactory` client and pass it in; correlation/trace propagation is applied on the Benzene-message outbound path |
| **Distributed tracing** | W3C `traceparent`/`tracestate` inbound extraction on HTTP **and** async transports (SQS, SNS, Kafka — AWS Lambda, Azure Functions, and the self-hosted worker — and Event Hub, Azure Functions and the self-hosted worker); OpenTelemetry, exporter-agnostic. The root `"W3CTraceContext.Root"` span and the per-stage handler span are both marked `Error` (with the exception attached) when downstream code throws, so a failed request is never indistinguishable from a successful one in a trace viewer. `ICorrelationId`/`InboundCorrelationIdMiddleware` bound and sanitize a caller-supplied correlation-id header (length-capped, control characters incl. `\r`/`\n` rejected) before it reaches a log scope or an outbound header, falling back to the self-generated id on rejection. | Sampling/backend-specific configuration (Jaeger, Application Insights, etc.) is yours to wire — Benzene exports via the standard OTel API, it doesn't ship a backend | `.UseW3CTraceContext()` as the first middleware on any pipeline continues a caller's trace instead of starting a new one per hop. See [Monitoring & Diagnostics](monitoring.md) and the [distributed tracing cookbook](cookbooks/distributed-tracing-opentelemetry.md). |
| **Retry-on-handler-failure-result** | Per-transport: some retry a returned `IBenzeneResult` failure (`IsSuccessful == false`) the same as an exception by default; some only retry it if you opt in; some can't retry it at all today. See the breakdown below — **the default is not uniform across transports, and on several it's silently unsafe.** | A single cross-transport reliability abstraction — retry semantics are inherently transport-native (Lambda batch-item-failure vs. Service Bus abandon vs. EventBridge destinations), so Benzene surfaces each transport's own mechanism rather than inventing one | Know your transport's default (below); opt in where an `Options`/`AckMode` knob exists; if none exists, have the handler throw instead of returning a failure result for anything that must be retried. **Any handler that can be retried needs to be idempotent** — see the Idempotency row above. |
| **Multi-tenancy** | *(nothing as a framework feature today)* | — (a candidate for post-1.0) | Roll a tenant-resolver middleware + a scoped tenant holder (the documented [Multi-Tenancy](cookbooks/multi-tenancy.md) pattern) |
| **AuthN / AuthZ** | OAuth2 bearer (JWT) validation with a strict algorithm allowlist + scope-based authorization (`Benzene.Auth.OAuth2`); signing keys are resolved via full OIDC discovery (`Authority`) or a bare JWKS document (`JwksUri`), both cached with refresh-on-unrecognized-`kid` (`OAuth2ConfigurationManagerFactory`/`JwksOnlyConfigurationRetriever`). `OAuth2BearerOptions.Validate()` fails fast at wire-up (not on the first request) on: a non-`https` `Authority`/`JwksUri` unless `RequireHttpsMetadata` is explicitly `false`; a null/whitespace/`"*"` entry in `ValidIssuers`/`ValidAudiences`; a `ValidAlgorithms` entry that is `"none"` or not one of the standard JWS signing algorithms (`Microsoft.IdentityModel.Tokens.SecurityAlgorithms`'s HS/RS/ES/PS 256/384/512 constants); and a `ClockSkew` above `OAuth2BearerOptions.MaxClockSkew` (15 minutes). `Benzene.Auth.Core`'s role/policy authorization (`RequireRole`/`RequirePolicy`/`RequireAuthorization`) reads roles via a single `RoleClaims` helper (`ClaimTypes.Role`/`role`/`roles`, the last also expanding a JSON-array value — Azure AD's app-roles shape) that `deploy/Mesh/Benzene.Mesh.Host`'s `MeshAuthGate` shares rather than reimplementing, so both agree on what counts as a role | Ship a policy-engine (OPA/Cedar) adapter, or rate-limiting middleware | Add an authorization middleware calling your policy engine; the `Benzene.Auth.Core` seams are there to build on |

### Retry-on-handler-failure-result — the per-transport breakdown

"Failure result" below means your handler returned `IsSuccessful == false` (e.g.
`BenzeneResult.ServiceUnavailable(...)`) — **not** a thrown exception. Every transport in Benzene
retries an unhandled *exception* by default (that's what makes it propagate to the host's own
retry machinery); what varies is what happens to a *returned* failure result, which is the
surprising case because nothing crashed.

| Transport | Default on a returned failure result | Opt-in fix |
|---|---|---|
| AWS Lambda SQS (`Benzene.Aws.Lambda.Sqs`) | **Safe** — retried per-message via `ReportBatchItemFailures`, same as an exception | N/A (default is already safe); `SqsOptions.BatchFailureMode = FailWholeBatch` to change the *shape* of the retry, not to enable it |
| AWS DynamoDB Streams (`Benzene.Aws.Lambda.DynamoDb`) | **Safe** — sequential processing stops at the first failed record and reports it for redelivery | N/A |
| AWS Kinesis (`Benzene.Aws.Lambda.Kinesis`) | **Safe by design** — the stream checkpoints only where your handler explicitly checkpoints; an unfailed-but-uncheckpointed record is redelivered. The checkpointer tracks a **contiguous-prefix** watermark (round 17, `#273`), not a single monotonic max-index one: the resume point is the first *unconfirmed* record's position, so a handler using `StreamOperators.PartitionBy` (this package's own recommended pattern for restoring per-key ordering) can never have an earlier, still-failed record silently skipped just because a later record from a different partition group was checkpointed first. Accepted tradeoff: a record confirmed ahead of an earlier gap is redelivered even though it already succeeded (safe over-retry, at-least-once) — for a plain sequential handler with no gaps, behavior is byte-identical to the old watermark | N/A — see [Benzene.Aws.Lambda.Kinesis's CLAUDE.md](../src/Benzene.Aws.Lambda.Kinesis/CLAUDE.md) |
| AWS SNS (`Benzene.Aws.Lambda.Sns`) | **Safe by default** — `SnsOptions.RaiseOnFailureStatus` defaults `true`, escalating a failure result into a throw so SNS's subscription retry/redrive applies; a `null`/unset result (pipeline completed without any middleware setting an outcome) escalates the same way, not silently accepted. `SnsOptions.CatchExceptions = true` still can't swallow an infrastructure/DI-wiring failure (`BenzeneResolutionException`) — it rethrows unconditionally, because SNS has no partial-failure channel, so swallowing it would report every message healthy while all of them fail the same way | `SnsOptions.RaiseOnFailureStatus = false` for at-most-once — see [SNS Fan-Out Pattern](cookbooks/sns-fan-out.md) |
| AWS EventBridge (`Benzene.Aws.Lambda.EventBridge`) | **Safe by default** — `EventBridgeOptions.RaiseOnFailureStatus` defaults `true`, escalating a failure result into a throw so EventBridge's retry/DLQ applies; a `null`/unset result escalates the same way. `EventBridgeOptions.CatchExceptions = true` still can't swallow an infrastructure/DI-wiring failure — it rethrows unconditionally, the same carve-out as SNS/S3 | `EventBridgeOptions.RaiseOnFailureStatus = false` for at-most-once |
| AWS Kafka/MSK (`Benzene.Aws.Lambda.Kafka`) | **Safe by default** — `KafkaOptions.BatchFailureMode` defaults to `PartialBatchFailure`, reporting each failed partition's resume offset via the batch response (needs `ReportBatchItemFailures` on the event source mapping, as with SQS) so records are redriven from the failure, honouring per-partition ordering | `KafkaOptions.BatchFailureMode = FailWholeBatch` (throws) when the event source mapping isn't configured for `ReportBatchItemFailures` |
| AWS S3 (`Benzene.Aws.Lambda.S3`) | **Safe by default** — `S3Options.RaiseOnFailureStatus` defaults `true`, escalating a failure result into a throw so the Lambda invocation fails and the event's async retry/DLQ applies; a `null`/unset result escalates the same way. `S3Options.CatchExceptions = true` still can't swallow an infrastructure/DI-wiring failure — it rethrows unconditionally, the same carve-out as SNS/EventBridge | `S3Options.RaiseOnFailureStatus = false` for at-most-once |
| AWS SQS self-hosted worker (`Benzene.Aws.Sqs`'s `SqsConsumer`) | **Safe by default** — `SqsConsumerOptions.AckMode` defaults to `SqsConsumerAckMode.PerMessage`, so only successfully-handled messages are deleted and a failure result is left for redelivery | `SqsConsumerAckMode.WholeBatch` for at-most-once (delete the whole batch regardless) |
| RabbitMQ self-hosted worker (`Benzene.RabbitMq`) | **Safe by default** (`RabbitMqAckMode.Explicit`) — a failure result (or exception) nacks the message for requeue/dead-letter, not ack | N/A (default is already safe); `RequeueOnFailure`/`AckMode` tune *how* it's redelivered, or `AckMode = AutoAck` to opt into at-most-once |
| Azure Service Bus Function trigger (`Benzene.Azure.Function.ServiceBus`) | **Safe by default** — although `AckMode` defaults to `AutoComplete`, `ServiceBusOptions.RaiseOnFailureStatus` defaults `true`, so a failure result throws (→ the message is abandoned, not completed). Under `AckMode = Explicit`, `state.Acked` is set only *after* the `CompleteMessageAsync`/`AbandonMessageAsync` settle call itself returns successfully (`ServiceBusApplication.OnPipelineSucceededAsync`) — a throwing settle call is exactly the case the base class's exception-recovery fallback-abandon exists for, and setting `Acked` up front used to skip it. Like every sibling sharing `AzureFunctionBatchApplicationBase`, `CatchExceptions = true` still can't swallow an infrastructure/DI-wiring failure (`BenzeneFailure.IsInfrastructure`) — it rethrows unconditionally after logging (#257 fix, mirroring AWS SNS/S3/EventBridge's #228), composing with the Explicit-ack abandon hook (abandon still happens, then the invocation fails loudly); the same catch also lets a genuine ambient `OperationCanceledException` (this call's own cancellation token, not an unrelated one) escape containment rather than being logged as an ordinary per-item failure (#258 fix), consistent with an already-*queued* item's #230 abort behavior | `RaiseOnFailureStatus = false` for at-most-once; `AckMode = Explicit` for true per-message complete/abandon control |
| Azure Service Bus self-hosted worker (`Benzene.Azure.ServiceBus`) | **Safe by default** — `BenzeneServiceBusConfig.AckMode` defaults to `ServiceBusConsumerAckMode.Explicit`, so a failure result (or throw) abandons the message for redelivery. Under `AckMode = Explicit`, settlement (`SettleAsync` — complete/abandon/dead-letter/defer) now runs *after* and *outside* the handler's own try/catch (#277): a settlement failure following a successfully-processed message (e.g. the lock was lost by the time settlement runs) is logged as a distinct settlement failure naming the message id, not misattributed to the handler, and does not trigger an abandon on a message that was already correctly processed — the lock is left to expire naturally so Service Bus redelivers it. A settlement failure for a message whose handler itself had failed keeps the prior log-and-propagate behavior unchanged | `AckMode = ServiceBusConsumerAckMode.AutoComplete` for at-most-once |
| Azure Kafka/Event Hubs Function trigger (`Benzene.Azure.Function.Kafka`) | **Safe by default** — `KafkaOptions.RaiseOnFailureStatus` defaults `true`, escalating a failure result into a throw so the trigger re-delivers. Shares `AzureFunctionBatchApplicationBase`'s #257/#258 fixes above: `CatchExceptions = true` rethrows an infrastructure/DI-wiring failure and a genuine ambient cancellation instead of swallowing either | `KafkaOptions.RaiseOnFailureStatus = false` for at-most-once |
| Azure Event Grid (`Benzene.Azure.Function.EventGrid`) | **Safe by default** — `EventGridOptions.RaiseOnFailureStatus` defaults `true`, escalating a failure result into a throw so Event Grid's retry/dead-letter (backoff up to 24h) applies. Shares `AzureFunctionBatchApplicationBase`'s #257/#258 fixes above: `CatchExceptions = true` rethrows an infrastructure/DI-wiring failure and a genuine ambient cancellation instead of swallowing either | `EventGridOptions.RaiseOnFailureStatus = false` for at-most-once |
| Azure Event Hubs Function trigger (`Benzene.Azure.Function.EventHub`) | **Safe by default** — `EventHubOptions.RaiseOnFailureStatus` defaults `true`, escalating a failure result (on both the property-based and envelope routing paths) into a throw so the trigger re-delivers the batch. Shares `AzureFunctionBatchApplicationBase`'s #257/#258 fixes above: `CatchExceptions = true` rethrows an infrastructure/DI-wiring failure and a genuine ambient cancellation instead of swallowing either | `EventHubOptions.RaiseOnFailureStatus = false` for at-most-once |
| Azure Queue Storage (`Benzene.Azure.Function.QueueStorage`) | **Safe by default** — `QueueStorageOptions.RaiseOnFailureStatus` defaults `true`, escalating a failure result (on both the preset-topic and envelope routing paths) into a throw so the host's `maxDequeueCount` retry/poison handling applies. Shares `AzureFunctionBatchApplicationBase`'s #257/#258 fixes above: `CatchExceptions = true` rethrows an infrastructure/DI-wiring failure and a genuine ambient cancellation instead of swallowing either | `QueueStorageOptions.RaiseOnFailureStatus = false` for at-most-once |
| Azure Timer trigger (`Benzene.Azure.Function.Timer`) | **Visible by default, not redeliverable** — `TimerOptions.RaiseOnFailureStatus` defaults `true`, escalating a failure result into a thrown `TimerMessageProcessingException` (#231 fix) so the Functions host records a failed invocation (retry/alerting per your monitoring, not Benzene) instead of completing silently; unlike every queue-shaped transport above, a failed tick is never redelivered by the platform either way — the next occurrence just runs on schedule, so the flag only controls whether the failure is *visible*, not whether it's retried. `TimerOptions.CatchExceptions = true` still can't swallow an infrastructure/DI-wiring failure — it rethrows unconditionally after logging (#257 fix, independent of but mirroring the batch-trigger family's) | `TimerOptions.RaiseOnFailureStatus = false` to accept a failure result without raising; `TimerOptions.CatchExceptions = true` to also contain a thrown exception instead of failing the invocation |
| Google Cloud Pub/Sub (`Benzene.GoogleCloud.Functions.PubSub`) | **Safe by default** — `PubSubOptions.RaiseOnFailureStatus` defaults `true`, escalating a failure result into a throw so Pub/Sub redelivers per the subscription's ack-deadline/retry policy; a `null`/unset result (round 17, `#275`) escalates the same way, not silently accepted — unlike the AWS single-context transports' equivalent fix, Pub/Sub delivers exactly one message per invocation with no batch-level fallback, so this transport had no safety net at all before the fix | `PubSubOptions.RaiseOnFailureStatus = false` for at-most-once |
| Kafka self-hosted worker (`Benzene.Kafka.Core`) | **At-most-once by default** — a stream worker (see the callout below) can't redeliver one record without halting, so `BenzeneKafkaConfig.CommitOnlyOnSuccess` defaults `false`: offsets auto-commit regardless of outcome, so a failed record is skipped on restart (a returned failure result is at least logged — `RaiseOnFailureStatus` defaults `true`) | `BenzeneKafkaConfig.CommitOnlyOnSuccess = true` (requires `CatchHandlerExceptions = false`) for at-least-once — offsets are then stored only after a successful handle, so a restart redelivers the failed record; or wire a `DeadLetterTopic`. **The 1.0 settlement contract** (maintainer-approved 2026-07-21): every **queue-shaped** transport is
**safe by default** — a handler that *returns* a failure `IBenzeneResult` (rather than throwing) is
**not settled by default**; it is escalated as that transport's `*MessageProcessingException` so the
platform redelivers it (at-least-once), instead of being silently acked/completed/checkpointed past
(at-most-once). Mechanically, `RaiseOnFailureStatus` defaults `true` on every queue-shaped options
type (AWS Lambda SNS/S3/EventBridge; the Azure Functions Kafka, Queue Storage, Event Grid, Event Hub
and Service Bus triggers; the self-hosted Event Hub worker; Google Cloud Pub/Sub), while
`Benzene.Aws.Sqs` (`AckMode = PerMessage`), `Benzene.Azure.ServiceBus` and `Benzene.RabbitMq`
(`AckMode = Explicit`) were already safe, and Kinesis / DynamoDB Streams settle via
`ReportBatchItemFailures` instead. Each transport exposes an explicit opt-out (the "Opt-in fix" column
shows the reverse) for the at-most-once cases where you deliberately want a returned failure accepted.
`SettlementContractDefaultsTest` guards these defaults against drift; the migration record behind this
contract is archived at `work/archive/settlement-contract-1.0-2026-07.md`.

**The two self-hosted *stream* workers are the deliberate exception — they default to at-most-once.**
A stream (a Kafka partition, an Event Hub partition) has no per-message ack/abandon: the only way to
*not* lose a failed record is to stop the worker and never advance the offset/checkpoint past it. That
is far too drastic a default (one poison record would halt all processing), so `Benzene.Kafka.Core`
(`CommitOnlyOnSuccess = false`) and `Benzene.Azure.EventHub` (`CatchHandlerExceptions = true`) default
to **skip-and-continue** — a failed record is logged and the stream advances past it. Opt into
at-least-once with `CommitOnlyOnSuccess = true` / `CatchHandlerExceptions = false` respectively, and
accept that a poison record then wedges/halts the worker until it's handled or dead-lettered. This is
a genuine property of streams, not an oversight — the **Lambda/Functions** stream *triggers* (Kinesis,
DynamoDB Streams, the Kafka/Event Hub Function triggers) can be safe-by-default because the platform
re-invokes them from the un-advanced checkpoint without any single process having to halt; a
long-running self-hosted worker has no such external re-invoker.

The rows marked N/A above (Cosmos DB Change Feed, HTTP) have no per-item async-retry knob to opt into
— there, a handler that `throw`s is the escape hatch for anything that must redeliver.

Each failed shard carries its own failure reason — `FailedShards` is `IReadOnlyList<FailedShard<TShard>>` (shard + the `Exception?` its worker call threw, `null` for an unsuccessful-result failure), and a thrown `ScatterGatherPartialFailureException` aggregates every reason onto `InnerException` (an `AggregateException`) plus a per-shard `Failures` list, so which shard failed and why is diagnosable from the exception alone. `BoundedFanOut.WhenAllAsync` itself now accepts an optional `CancellationToken` (#230 fix) that a queued shard behind `MaxDegreeOfParallelism` observes while waiting for a free slot — every batch trigger built on it (`AzureFunctionBatchApplicationBase`, `MiddlewareMultiApplication`) propagates its own ambient token through; `ScatterGatherAsync`'s own public signature has no `CancellationToken` parameter yet, so it currently passes `default` (no shard observes cancellation via this path today) | Ship a dedicated scatter-gather engine or framework — this is the thin, supported composition of parts Benzene already has (`SendAsync` + `BoundedFanOut`), kept to one method, options, and a result on purpose. Built-in hierarchical fan-out for very large shard counts | For very large fan-outs, shard hierarchically yourself — a coordinator scatters to partition workers that each scatter and reduce locally, the same `ScatterGatherAsync` call at each level |
| **Rate limiting** | `Benzene.RateLimiting` — `RateLimitingMiddleware<TContext>` built directly on `System.Threading.RateLimiting`'s abstract `RateLimiter` (BYO fixed/sliding window, token bucket, concurrency, or custom limiter); never queues (`QueueLimit = 0` on every built-in) so a rejection is immediate, not memory pressure; convenience entry points `UseFixedWindowRateLimiting`, `UseTokenBucketRateLimiting`, `UsePayloadSizeRateLimiting` (a bytes-per-second token bucket costing each message its UTF-8 body size, with a cheap `Content-Length`-based pre-check — a rate/CPU saving, **not** a memory bound: see [Rate Limiting](rate-limiting.md) for why); **per-caller partitioning** via `PartitionedRateLimitingMiddleware<TContext>`/`UsePartitionedRateLimiting` over a BYO `PartitionedRateLimiter<TContext>`, so one abusive caller can't exhaust the shared budget for everyone else (the key is caller-supplied and therefore spoofable, but strictly better than the single shared limiter every other entry point still uses by default); a rejected message short-circuits with `TooManyRequests` (→ HTTP 429), carrying the limiter's retry-after metadata in both the error message and a `Retry-After` response header when the limiter supplies it, and logging a warning when an `ILogger` is registered; the three convenience limiters' disposal is owned by the DI container, tracked **per pipeline** (keyed on the pipeline's own context type, not the shared container) so a service's sibling pipelines — e.g. `MiddlewarePipelineBuilder<T>.Create<TNewContext>()`'s documented multi-transport pattern, one container shared across API Gateway/BenzeneMessage/SQS/SNS/EventBridge — each get their own independent internally-owned limiter rather than colliding on one ambient registration; a caller-supplied/BYO limiter's disposal is always the caller's. An `ObjectDisposedException` from the cost delegate's own dependencies is reported distinctly from one thrown by the limiter itself being disposed — both still fail closed | Authoritative, fleet-wide rate limiting — every limiter instance is **per service instance**: a fleet of N instances admits up to N× the configured rate, and serverless scale-out multiplies it further. This package protects one instance from being a free denial-of-service/cost-amplification vector; it is not traffic shaping. `UsePayloadSizeRateLimiting` is a rate bound on oversized payloads, not a hard memory cap — ASP.NET Core hosts buffer the request body before this middleware ever runs | Put authoritative rate limiting at the gateway (API Gateway, APIM, ingress) in front of every instance; put a host-level body-size cap (Kestrel's `MaxRequestBodySize`, a gateway limit) in front of an endpoint where payload size is a genuine memory-exhaustion concern; see [Rate Limiting](rate-limiting.md) |
| **Conformance** | `test/Benzene.Conformance.Test` runs the vendored language-neutral fixtures in `test/conformance-fixtures/` (a `SPEC_VERSION`-stamped snapshot of the main repo's `docs/specification/conformance/`): envelope, HTTP + gRPC status mappings, status vocabulary, problem details, contract document/hash, and the mesh descriptor/trace/issue/collector/version-order shapes (`transport-metadata-cases.json` runs in `test/Benzene.Core.Test/Conformance/`); the `conformance-drift-check.yml` workflow re-verifies the vendored snapshot against the canonical repo | Edit a fixture to make this port pass — the fixture is the neutral truth | A mismatch is a bug here or a deliberate spec change there, never a fixture patch |

## Why "we don't do that" is a feature

Every deliberate "no" above buys you something: you keep the full power of the tool you chose,
you're never blocked by a leaky abstraction, and the surface you *do* depend on stays small and
stable. When you need something Benzene doesn't ship, the extension model (custom middleware,
custom pipes, the getter/setter mapper pattern) is a supported, documented path — see
[Middleware](middleware.md) and [Common Middleware](common-middleware.md).

If you find yourself wishing Benzene abstracted a transport or a database away, that's usually the
signal to reach for the SDK directly inside your handler — which is exactly where Benzene's design
wants that code to live.
